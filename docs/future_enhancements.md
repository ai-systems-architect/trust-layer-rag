# Future Enhancements — Trust Layer RAG

Next-layer improvements across four areas: evaluation, retrieval, governance, and
generation. Items here range from near-term production requirements to longer-term
architectural improvements. Some are also referenced in the README Future Work
section or `docs/architecture.md` — duplication is intentional; this document is
the single-page reference for enhancement planning.

---

## Evaluation

### Independent LLM Judge

**What:** Use a different model provider as the RAGAs evaluator — e.g., GPT-4o
to judge faithfulness and context precision scores for answers generated by Claude
via Bedrock.

**Why it matters:** The current evaluation uses Claude via Bedrock both to generate
answers and to judge them. This is the "grading your own homework" problem — same
model family may exhibit systematic leniency toward its own outputs. A cross-provider
judge produces a more credible benchmark, especially for external audiences and
compliance attestation contexts.

**What it requires:** Swap the `llm` parameter in the RAGAs evaluation config from
Bedrock Claude to OpenAI GPT-4o. The RAGAs framework supports pluggable LLM judges
— one config change. Adds approximately $0.005–0.015 per evaluation question in
GPT-4o judge cost.

*Also noted in: `docs/architecture.md` — Acknowledged Production Gaps.*

---

### Real User Query Sampling

**What:** Replace the 20-question hand-authored golden dataset with queries sampled
from real production traffic via Langfuse traces.

**Why it matters:** Hand-authored questions reflect what the author thinks users will
ask. Production traffic reveals actual query patterns — including edge cases, ambiguous
phrasings, and domain terminology the evaluation set missed. At 50+ queries/month, a
production-sampled evaluation set is feasible and more representative than any
manually constructed set.

**What it requires:** Langfuse trace export → sample query/answer pairs → manual
review to assign `relevant_chunk_ids` → re-run retrieval diagnostics against the new
set. The auto-labeling methodology in `evaluation/label_chunks.py` applies unchanged
— only the query source changes. Estimated effort: 2–3 hours of annotator review per
20-question refresh cycle.

---

### RAGAs as CI Gate

**What:** Run RAGAs faithfulness and context precision as automated checks on every
PR that touches retrieval, generation, or the system prompt.

**Why it matters:** Currently RAGAs is a manual, once-run benchmark with scores
locked. A faithfulness regression — model starts hallucinating after a prompt change
— would only be caught on the next manual evaluation run. A CI gate catches the
regression on the PR that introduced it, before it reaches production.

**What it requires:** GitHub Actions workflow that runs `evaluation/ragas_eval.py`
on a 5–10 question subset of the golden dataset (for cost), compares scores to locked
baselines (Faithfulness ≥ 0.85, Context Precision ≥ 0.90), and fails the build on
regression. Approximate cost: $0.10–0.25 per CI run at 10 questions. Trigger on
changes to `pipeline.py`, `generation/`, `retrieval/`, and `prompts/`.

## Retrieval

### HyDE — Hypothetical Document Embeddings

**What:** Instead of embedding the raw query, use an LLM to generate a short
hypothetical answer first, then embed that hypothetical answer for retrieval.

**Why it matters:** For abstract governance queries ("How does the AI RMF GOVERN
function establish accountability?"), the query text has low vocabulary overlap with
the answer chunks. Embedding a hypothetical answer closes the vocabulary gap — the
embedding space contains an answer-shaped vector rather than a question-shaped one.
Most likely to help on the Governance query category where MRR is 0.8750 semantic
baseline.

**What it requires:** One additional Bedrock Claude call at `temperature=0.3` before
the embedding step — generate a 2–3 sentence hypothetical answer, embed it, use that
vector for HNSW search. Falls back to standard query embedding on generation failure.
Adds approximately 100–250ms and $0.001 per query. The query enrichment stage
(DL-025) is the natural insertion point. Validate with retrieval diagnostics — measure
MRR improvement on Governance queries specifically.

*Also noted in: README Future Work — Query expansion / multi-query rewriting.*

### Adaptive Chunking

**What:** Use different chunk sizes per document type rather than the uniform
600-token / 100-overlap configuration applied to all four corpus sources.

**Why it matters:** NIST 800-53 control entries are self-contained, bounded units —
a 600-token chunk often spans multiple unrelated control enhancements, reducing
precision. AI RMF and AI 600-1 are dense narrative prose where 600 tokens is
appropriate. FedRAMP Baseline entries sit between the two. Optimal chunk boundaries
differ by document structure and would improve Context Precision on control-ID
queries where chunks currently straddle control boundaries.

**What it requires:** Per-source chunking config in `ingestion/chunk.py` — NIST
800-53 at 300–400 tokens (control-boundary aligned using control ID regex as a
natural split point), AI RMF / AI 600-1 at 600 tokens, FedRAMP at 400 tokens.
Requires full re-ingestion and re-labeling of the golden dataset (`label_chunks.py`).
Measure Context Recall and Context Precision improvement before committing — the
benefit may not justify re-ingestion cost at current corpus size.

### Connection Pooling for Concurrent Load

**What:** Add a `ThreadedConnectionPool` (max ~5 connections) to the psycopg2
connection management in `retrieval/semantic.py`.

**Why it matters:** FastAPI runs synchronous route handlers in a thread pool.
Under concurrent load, multiple threads can open simultaneous psycopg2 connections
with no upper bound — one new connection per in-flight request. For the current
single-consumer model (trust-layer-agent calling `/retrieve` serially) this is
fine. It becomes a real risk in trust-layer-orchestration, where parallel
sub-agents will call `/retrieve` concurrently within a single orchestration run,
potentially exhausting database connection limits.

**What it requires:** Replace the `get_connection()` pattern in
`retrieval/semantic.py` with a `ThreadedConnectionPool` initialized at module
load time (min=1, max=5). Callers acquire a connection with `getconn()` and
release it with `putconn()` in a `finally` block. Connection limit of 5 is
sufficient for sub-agent parallelism; tune upward based on RDS instance connection
limits if needed.

### Raise top-k from 5 to 8

**What:** Increase the number of reranked chunks passed to generation from 5 to 8.

**Why it matters:** Context Recall at 0.75/0.76 is the weakest RAGAs metric — some
relevant chunks exist in the corpus but fall outside the top-5. The ground truth pool
averages 28 chunks per question; top-5 captures 17%. Raising to top-8 directly
improves coverage with minimal architectural change.

**What it requires:** Change `TOP_K_RERANK` in `config.py` from 5 to 8. Single
config value change. Cost impact: Cohere charges per-document on the candidate set
(10 chunks), not per top-k returned — rerank cost is unchanged. Claude context window
grows by ~3 chunks, adding approximately $0.001–0.003 per query. Re-run retrieval
diagnostics and RAGAs after the change to confirm Context Recall improves and
Faithfulness holds under the larger context.

## Governance

### Topic Policy in Bedrock Guardrails

**What:** Add a `topicPolicy` to the Bedrock Guardrail that explicitly denies
off-topic queries at the input gate before the pipeline fires.

**Why it matters:** Off-topic queries (cryptocurrency, blockchain, quantum computing,
non-federal frameworks) are currently handled by corpus grounding — retriever finds
nothing, Cohere rerank scores near zero, Claude declines. This works correctly but
costs the full pipeline: OpenAI embedding call, HNSW search, BM25 search, Cohere
rerank, Bedrock generation. A topic policy blocks the query at `apply_guardrail`
for one Bedrock call (~50ms, ~$0.0008) instead of the full 8–13s pipeline. Savings
grow in absolute terms at scale.

**What it requires:** Add `topic_policy_config` to `aws_bedrock_guardrail.compliance`
in `infrastructure/main.tf`. Define denied topics using natural language descriptions
(Bedrock topic policies are description-based, not keyword lists): cryptocurrency and
blockchain, quantum computing cryptography, non-federal governance frameworks,
system-specific compliance assessment. After deploying, re-run
`evaluation/guardrail_test.py` — all 5 negative cases must still pass under the
new policy. Verify that the 20-question positive evaluation set is not blocked.

*Also noted in: `docs/architecture.md` — off-topic handling currently relies on
retrieval grounding.*

### Corpus Version Co-Versioning with Golden Dataset

**What:** Tie golden dataset versions to corpus versions — when NIST publishes an
updated SP 800-53 or FedRAMP revises the Moderate Baseline, corpus re-ingestion and
golden dataset re-labeling are gated together as a release artifact.

**Why it matters:** Currently corpus freshness monitoring is manual via corpus_hash
discipline. If the corpus is re-ingested with updated documents but the golden dataset
is not re-labeled, `relevant_chunk_ids` in `golden_dataset.json` may reference chunks
that no longer exist or have shifted content — evaluation scores become unreliable
without any visible signal that something changed.

**What it requires:** Add a `corpus_version` field to `evaluation/golden_dataset.json`
that matches a `corpus_hash` recorded at ingestion time. Add a CI pre-flight check
in `retrieval_diagnostics.py` and `ragas_eval.py` that warns (or fails) if
`corpus_version` does not match the current corpus hash. Document re-labeling as a
required release checklist step whenever corpus is refreshed.

*Also noted in: `docs/architecture.md` — Acknowledged Production Gaps.*

### Natural Language Autoencoders (NLA) for Model Introspection

**What:** Add NLA-based introspection to detect unverbalized reasoning or hidden
model motivations during high-stakes compliance queries — surfacing what the model
"considered" internally but did not output.

**Why it matters:** Output guardrails verify what Claude returns. NLAs would verify
how it got there — did it reason from retrieved chunks or from parametric memory?
Did it internally consider factors it didn't cite? For compliance contexts where
overclaiming is the primary failure mode, a deeper audit trail beyond output
grounding is a meaningful governance control. NLAs can surface reasoning patterns
that faithfulness scores miss — a response can be technically grounded in retrieved
chunks while still reflecting model priors that weren't visible in the output.

**What it requires:** This is research-stage capability. Anthropic's mechanistic
interpretability work (sparse autoencoders, feature extraction) is the foundation,
but there is no shipping API today. The production path depends on Anthropic
exposing interpretability tooling via Bedrock or the Anthropic API — likely 12–24
months out. When available: integration would wrap the `generate()` call in
`generation/generate.py` with a pre/post introspection call on high-impact queries.
Cost consideration: NLA introspection requires running encoder/decoder passes
over activations — estimated 2–3× inference cost. Governance decision required:
introspect on every query, high-impact queries only, or risk-triggered sampling?
Budget allocation for "explainability overhead" becomes a first-class architecture
decision. See DL-030 (reserved — cost-governance tradeoffs for advanced
explainability).

## Generation

### Streaming — converse_stream()

**What:** Replace `converse()` with `converse_stream()` in `generation/generate.py`
for token-by-token streaming to the Streamlit UI.

**Why it matters:** Current generation latency is 7–12s for a full response. Total
latency does not change, but perceived latency drops dramatically — the user sees the
first words in 1–2s rather than waiting for a full response. Highest-impact UX
improvement available without any architectural changes. Compliance responses are
long (multi-paragraph, cited) — streaming benefit is proportionally larger than for
short chat responses.

**What it requires:** Replace `converse()` with `converse_stream()` in
`generation/generate.py`. Streamlit's `st.write_stream()` handles progressive
rendering natively. Two complications: (1) with streaming, the guardrail action
arrives at the end of the stream rather than as a synchronous response — need to
buffer the full response before applying the output guardrail check; (2) PII scrub on
output must apply to the buffered full response, not to individual tokens. Both are
solvable without structural changes.

*Also noted in: `docs/architecture.md` — Latency Optimization Levers.*

### Intent Routing — Haiku for Control ID Lookups

**What:** Classify query intent before generation and route control-ID lookups
(AC-6, IR-4, SC-28) to Claude Haiku instead of Sonnet.

**Why it matters:** Architect-level synthesis queries ("How does FedRAMP access
control align with AI RMF governance?") require Sonnet. "What does AC-6 require?"
does not — the answer is a direct retrieval from control text that Haiku handles
accurately. Haiku generates 2–3× faster and costs approximately 80% less per query.
At a 50% control-ID query mix, overall generation cost drops 30–40% and median
latency drops meaningfully.

**What it requires:** A lightweight intent classifier at the query enrichment stage
(DL-025 is the insertion point — intent classification can run alongside pronoun
resolution). Rule-based first pass: queries matching `_CONTROL_ID_RE` with no
cross-framework language → Haiku. Governance and cross-corpus queries → Sonnet.
The model identifier is already env-driven in `config.py` — routing is a conditional
model selection, not an architectural change. Validate that Haiku faithfulness on
control-ID queries meets the ≥ 0.85 target before enabling.

*Also noted in: README Future Work — Structured intent extraction, and
`docs/architecture.md` — Latency Optimization Levers and Cost.*

### Retrieval-Augmented Persistent Memory

**What:** Extend the current within-session conversation window (last 6 messages,
DL-025) to persistent multi-session memory stored in RDS and retrieved via semantic
search at query time.

**Why it matters:** A compliance analyst researching FedRAMP authorization over
multiple sessions re-explains their system context on every new session. Persistent
memory retrieves relevant prior session context — "working on an AWS GovCloud
deployment at Moderate impact level targeting AC and SC families" — and injects it
into the query enrichment stage. Transforms the system from a stateless reference
tool into a research assistant with continuity.

**What it requires:** `user_sessions` table in RDS (user_id, session_id, message,
embedding, timestamp). At query time: embed the query, retrieve top-3 semantically
similar prior messages from the user's history, prepend to conversation history before
query enrichment runs. Privacy consideration: session memory contains user-supplied
system descriptions — PII scrubbing must apply to stored messages, not just transient
queries. The within-session memory foundation from DL-025 is the right starting point;
persistence is an extension of the same pattern.

*Also noted in: README Future Work — System-specific compliance assistant.*

## Cross-Project Integration

### trust-layer-rag → trust-layer-agent Governed Knowledge Service

Several enhancements above are architected with trust-layer-agent integration
in mind. The design principle: **trust-layer-rag enhancements that improve cost
control, retrieval precision, and evaluation independence directly improve
trust-layer-agent's viability as a governed agent architecture.** Governance is
layered, not duplicated — trust-layer-rag governs what knowledge enters the
system, trust-layer-agent governs what the agent does with it.

**Retrieval-Augmented Persistent Memory** — trust-layer-agent's evidence
collection workflow will call trust-layer-rag's retrieval API (`POST /retrieve`)
across multiple agent runs. Persistent memory enables the agent to build context
over time — system scope, control family, impact level — without re-establishing
it on every tool invocation. Without this, each agent run starts cold regardless
of prior work.

**Independent LLM Judge** — when trust-layer-agent uses trust-layer-rag as a
governed knowledge service, evaluation independence matters more, not less. If
trust-layer-rag's evaluation judge is the same model family trust-layer-agent uses
for reasoning, cross-system validation becomes circular — one Claude instance
validating another Claude instance's outputs. An independent judge (different
provider) breaks that circularity.

**Intent Routing (Haiku vs. Sonnet)** — trust-layer-agent's
`lookup_compliance_requirement` tool will fire multiple times per agent run,
potentially 5–10 retrieval calls in a single evidence collection workflow. Intent
routing reduces per-tool-call cost significantly — especially important when the
agent makes repeated lookups across the same control family in a single run.

**HyDE and Adaptive Chunking** — agent-generated tool call queries have different
vocabulary patterns than human-authored queries. Queries synthesized by the agent
mid-workflow ("retrieve evidence for AC-6 implementation at Moderate impact in
cloud-hosted systems") are more structured but less natural than user queries. HyDE
and adaptive chunking improve retrieval quality when the query source is
agent-generated rather than human-authored.
